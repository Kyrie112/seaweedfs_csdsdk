# 单步开发的标准流程(SOP)

本文件规定"一个开发步骤"应该怎么走。`PROGRESS.md` 中的每个 T 编号任务都遵循同一套流程,
以保证记录可比较、可复核。

## 1. 七步流程

```text
① 登记 → ② 前置确认 → ③ 设计冻结 → ④ 实现
                            ↓
        ⑦ 记录提交 ← ⑥ 端到端验证 ← ⑤ 自测回归
```

### ① 登记

- 在 `PROGRESS.md` 把该步骤状态改为 🟡,填写开始日期;
- 若发现前置未满足,直接标 ⛔ 并写明阻塞项,不进入下一步。

### ② 前置确认

- 确认该步骤依赖的开放问题(Qx)已解决;
- 确认依赖步骤的产出物真实可用(不是"应该可用");
- 需要决策的,先在当日 `journal/` 里记录决策与理由。

### ③ 设计冻结

- 明确**接口层面的变化**:新增字段名、错误码、响应头、参数名;
- 明确**兼容性策略**:老调用方 / 老 agent / 老内核如何表现;
- 写入对应 `Mx-*.md` 的步骤小节,作为实现的依据。

> 冻结的意思是:实现阶段不再改接口。确需修改时,回到本步重走。

### ④ 实现

- 以"最小改动"为原则,优先复用已有机制(如 `params` 下推、现有错误处理);
- 保持既有语义不变:默认路径的行为不得因新功能而改变;
- 新增分支必须有明确的失败语义(不允许"忽略后继续")。

### ⑤ 自测回归

必须至少运行并记录以下三类:

| 类型 | 命令示例 | 通过标准 |
| --- | --- | --- |
| 单元测试 | `go test ./weed/server/ -run '<相关>'` | 新增用例通过,旧用例不回归 |
| 设备侧参考测试 | `make -C smartssd test` | 全部检查通过(当前基线 491 项) |
| 构建 | `go build ./weed/...`、`make -C smartssd syntax-check` | 无错误、无新增告警 |

### ⑥ 端到端验证

- 用实验台跑真实链路:`csd-experiments/scripts/run_image_search_experiment.sh`
  或 `run_phase1_local.sh`;
- 一致性相关步骤**必须**包含一次故障注入(见 `M4-verification.md` 的 F1–F7 矩阵);
- 记录:命令、原始输出、关键指标(时延、失败类型、是否出现静默错误)。

### ⑦ 记录与提交

- 按 `templates/step-record.md` 写一份步骤记录;
- 在当日 `journal/` 追加进展(含踩坑与决策);
- 更新 `PROGRESS.md` 状态为 ✅ 并链接证据;
- **同一个提交**内包含:代码 + 步骤记录 + 进度更新。

## 2. 完成定义(DoD)

一个步骤只有同时满足以下全部条件才算完成:

- [ ] 代码已实现且默认路径行为不变
- [ ] 接口变化已写入设计文档并冻结
- [ ] 新增单元测试覆盖正例与反例(尤其失败路径)
- [ ] 既有回归全部通过(服务端 + 设备侧)
- [ ] 端到端验证通过,含一次故障注入
- [ ] 性能影响已测量并落在预算内(默认 < 5%,特殊步骤另定)
- [ ] 步骤记录与 journal 已写,证据可复现(命令 + 输出)
- [ ] `PROGRESS.md` 状态与证据链接已更新

## 3. 分支与提交约定

| 项目 | 约定 |
| --- | --- |
| 分支 | 在 `feat/csd-native-compute` 上继续,或切 `feat/consistency-m1` 等专用分支 |
| 提交粒度 | 一个步骤一个提交;同一提交包含代码 + 记录 |
| 提交信息 | `feat(consistency): <步骤ID> <做了什么>`;涉及行为变化时在正文写清兼容性 |
| 回滚 | 每个步骤必须写明回滚方式(通常为 revert 该提交;涉及数据结构的需额外说明) |

## 4. 必须留痕的信息

为保证"结论可复核",任何记录不得缺少以下要素:

1. **命令**:可直接复制执行;
2. **原始输出**:关键片段(不是转述);
3. **数据文件**:若产生新的 CSV/日志,写明路径;
4. **结论**:一句话说明"这个结果意味着什么";
5. **反例**:若验证中发现反例,必须原样记录,不得只写"已修复"。
