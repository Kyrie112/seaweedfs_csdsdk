# 第二阶段:下沉判决成本模型与 break-even 分析

> 对应后续工作计划中的 **P0-1(成本模型)**。
> 数据来源:`results/image_search_*.csv`;拟合脚本:
> [`scripts/fit_cost_model.py`](../scripts/fit_cost_model.py)。
> 前置:[第一阶段一致性证明与消融设计](第一阶段-一致性证明与消融设计.md)。

## 0. 结论摘要

- 建立了两条线性成本模型并给出 **break-even 不等式**;
- 用已有实测数据拟合:近存路径 **1.759 ms/MiB**,主机路径 **124.75 ms/MiB**
  (含 Python 客户端计算);
- 在本次测量区间(4–64 MiB)内**没有正交叉点**:近存路径在所有测试规模上都占优;
- 模型同时给出"主机何时会反超"的**临界计算速率**:例如链路 1 GiB/s 时,
  主机需要 > **1318 MiB/s** 的扫描计算速率才能与近存路径打平。

---

## 1. 模型

设数据量为 `S`(MiB),主机路径与近存路径的端到端时延分别为:

```text
T_host(S) = L0_host + S / B_link + S / P_host
T_off(S)  = L0_off  + S / B_dev  + S / P_dev
```

| 符号 | 含义 |
| --- | --- |
| `L0_host` | 主机路径固定开销(建立连接、客户端初始化等) |
| `B_link` | 主机到存储的链路带宽(MiB/s) |
| `P_host` | 主机侧扫描/计算速率(MiB/s) |
| `L0_off` | 近存路径固定开销(调度、设备握手、结果回传) |
| `B_dev` | 设备读取速率(MiB/s) |
| `P_dev` | 设备内算子速率(MiB/s) |

合并成关于 `S` 的线性函数:

```text
T_host(S) = a_h * S + b_h,   a_h = 1/B_link + 1/P_host
T_off(S)  = a_o * S + b_o,   a_o = 1/B_dev  + 1/P_dev
```

### break-even 条件

主机路径更快当且仅当:

```text
a_h * S + b_h < a_o * S + b_o
⇔ (a_h - a_o) * S < b_o - b_h
```

于是:

```text
若 a_h <= a_o:主机路径在足够大的 S 上总是更快(或持平);
若 a_h >  a_o:存在交叉点 S* = (b_o - b_h) / (a_h - a_o),
               S < S* 时主机更快,S > S* 时近存更快。
```

**判据**:比较两条路径的**边际成本**(每 MiB 的时延),而不只是比较固定开销。

## 2. 参数估计

### 2.1 实测点

| 图库 | 近存路径(ms) | 主机路径(ms) |
| --- | --- | --- |
| 4 MiB | 16.49 | 505.50 |
| 16 MiB | 35.94 | 1978.68 |
| 64 MiB | 121.47 | 7988.25 |

### 2.2 拟合结果

```text
T_off(S)  = 8.72 ms + 1.7589 ms/MiB * S
T_host(S) = 0.00 ms + 124.7548 ms/MiB * S
```

- 近存路径:固定开销约 **8.7 ms**,边际成本 **1.76 ms/MiB**
  (等效约 570 MiB/s 的端到端扫描速率);
- 主机路径:边际成本 **124.75 ms/MiB**;
- 三条点的斜率差异约 **71 倍**,所以在本区间内近存路径全面占优,
  不存在正交叉点。

> **重要限定**:这里的"主机路径"包含 Python 客户端的描述子计算,
> 其 124.75 ms/MiB 主要反映**客户端计算能力**,而不是网络带宽上限。
> 因此该斜率不能直接外推为"主机永远更慢"。

## 3. 敏感性分析:主机何时会反超

主机边际成本 `a_h = 1000/B_link + 1000/P_host`(ms/MiB)。
令 `a_h = a_o = 1.7589`,可得临界主机计算速率:

| 链路带宽 | 临界主机计算速率 | 解读 |
| --- | --- | --- |
| 100 MiB/s | 主机已占优 | 链路太慢,搬数据不划算 |
| 500 MiB/s | 主机已占优 | 同上 |
| 1000 MiB/s | **1318 MiB/s** | 主机需约 1.3 GiB/s 的扫描速率才能打平 |
| 5000 MiB/s | 641 MiB/s | 链路变快后,主机更容易占优 |
| 10000 MiB/s | 603 MiB/s | 接近"纯计算受限"极限 |

**解读**:

- 本实验的主机路径(Python)远低于临界值,所以近存全面占优;
- 如果换成高度优化的 C/FPGA 主机算子(例如 2 GiB/s),
  在 1 GiB/s 链路上主机就会在**大文件**上反超;
- 这正好给出论文的"适用边界":**近存计算的收益取决于"链路慢 + 设备快"**,
  而不是绝对的"存储端一定更快"。

## 4. 预测与实测的对照

用拟合参数预测各规模的主机路径(仅作趋势验证):

| 规模 | 实测主机(ms) | 模型(ms) | 相对误差 |
| --- | --- | --- | --- |
| 4 MiB | 505.50 | 499.02 | −1.3% |
| 16 MiB | 1978.68 | 1996.08 | +0.9% |
| 64 MiB | 7988.25 | 7984.31 | −0.05% |

三点拟合的样本量很小,以上只能说明"线性模型在该区间是合理的",
不能作为强统计结论。后续应在真实集群上补充更多规模点。

---

## 5. 适用边界与威胁

| 威胁 | 影响 | 缓解 |
| --- | --- | --- |
| 只有 3 个数据点 | 截距与斜率不稳定 | 补充 8–128 MiB 多点 |
| 主机路径含 Python 计算 | 高估主机成本 | 用优化的 C/内核实现重测 |
| 共享容器环境 | 噪声大 | 真机 + 多次重复 |
| 不同算子的计算强度不同 | 模型参数不可通用 | 按算子类别分别拟合 `P_host/P_dev` |
| 缓存状态 | 冷/热差异大 | 按冷/热分别建模型 |

---

## 6. 结论

1. 本工作负载(图像检索扫描)在 4–64 MiB 区间内**明确处于近存占优区**;
2. 模型给出的判据不是"数据大就该下沉",而是
   **`1/B_link + 1/P_host` 与 `1/B_dev + 1/P_dev` 的比较**;
3. 当主机计算足够快(约 > 0.6–1.3 GiB/s,取决于链路)时,
   主机路径会在大文件上反超——这为"何时不该下沉"提供了定量边界;
4. 下一步:在 tan 集群/真机上补充规模点,按算子类别拟合参数,
   并把 break-even 相图作为论文的核心图之一。
