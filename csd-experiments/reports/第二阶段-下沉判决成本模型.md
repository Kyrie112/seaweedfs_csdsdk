# 第二阶段:下沉判决成本模型与 break-even 分析

> 对应后续工作计划中的 **P0-1(成本模型)**。
> 数据来源:`results/image_search_*.csv`;拟合脚本:
> [`scripts/fit_cost_model.py`](../scripts/fit_cost_model.py)。
> 前置:[第一阶段一致性证明与消融设计](第一阶段-一致性证明与消融设计.md)。

## 0. 结论摘要

- 建立了两条线性成本模型并给出 **break-even 不等式**;
- 用已有实测数据拟合:近存路径 **1.759 ms/MiB**,主机路径 **124.75 ms/MiB**
  (含 Python 客户端计算);
- 在本次测量区间(4–64 MiB)内**没有正交叉点**:近存路径在所有测试规模上都占优;
- 模型同时给出"主机何时会反超"的**临界计算速率**:例如链路 1 GiB/s 时,
  主机需要 > **1318 MiB/s** 的扫描计算速率才能与近存路径打平。

---

## 1. 模型

设数据量为 `S`(MiB),主机路径与近存路径的端到端时延分别为:

```text
T_host(S) = L0_host + S / B_link + S / P_host
T_off(S)  = L0_off  + S / B_dev  + S / P_dev
```

| 符号 | 含义 |
| --- | --- |
| `L0_host` | 主机路径固定开销(建立连接、客户端初始化等) |
| `B_link` | 主机到存储的链路带宽(MiB/s) |
| `P_host` | 主机侧扫描/计算速率(MiB/s) |
| `L0_off` | 近存路径固定开销(调度、设备握手、结果回传) |
| `B_dev` | 设备读取速率(MiB/s) |
| `P_dev` | 设备内算子速率(MiB/s) |

合并成关于 `S` 的线性函数:

```text
T_host(S) = a_h * S + b_h,   a_h = 1/B_link + 1/P_host
T_off(S)  = a_o * S + b_o,   a_o = 1/B_dev  + 1/P_dev
```

### break-even 条件

主机路径更快当且仅当:

```text
a_h * S + b_h < a_o * S + b_o
⇔ (a_h - a_o) * S < b_o - b_h
```

于是:

```text
若 a_h <= a_o:主机路径在足够大的 S 上总是更快(或持平);
若 a_h >  a_o:存在交叉点 S* = (b_o - b_h) / (a_h - a_o),
               S < S* 时主机更快,S > S* 时近存更快。
```

**判据**:比较两条路径的**边际成本**(每 MiB 的时延),而不只是比较固定开销。

## 2. 参数估计

### 2.1 实测点

| 图库 | 近存路径(ms) | 主机路径(ms) |
| --- | --- | --- |
| 4 MiB | 16.49 | 505.50 |
| 16 MiB | 35.94 | 1978.68 |
| 64 MiB | 121.47 | 7988.25 |

### 2.2 拟合结果

```text
T_off(S)  = 8.72 ms + 1.7589 ms/MiB * S
T_host(S) = 0.00 ms + 124.7548 ms/MiB * S
```

- 近存路径:固定开销约 **8.7 ms**,边际成本 **1.76 ms/MiB**
  (等效约 570 MiB/s 的端到端扫描速率);
- 主机路径:边际成本 **124.75 ms/MiB**;
- 三条点的斜率差异约 **71 倍**,所以在本区间内近存路径全面占优,
  不存在正交叉点。

> **重要限定**:这里的"主机路径"包含 Python 客户端的描述子计算,
> 其 124.75 ms/MiB 主要反映**客户端计算能力**,而不是网络带宽上限。
> 因此该斜率不能直接外推为"主机永远更慢"。

## 3. 敏感性分析:主机何时会反超

主机边际成本 `a_h = 1000/B_link + 1000/P_host`(ms/MiB)。
令 `a_h = a_o = 1.7589`,可得临界主机计算速率:

| 链路带宽 | 临界主机计算速率 | 解读 |
| --- | --- | --- |
| 100 MiB/s | 主机已占优 | 链路太慢,搬数据不划算 |
| 500 MiB/s | 主机已占优 | 同上 |
| 1000 MiB/s | **1318 MiB/s** | 主机需约 1.3 GiB/s 的扫描速率才能打平 |
| 5000 MiB/s | 641 MiB/s | 链路变快后,主机更容易占优 |
| 10000 MiB/s | 603 MiB/s | 接近"纯计算受限"极限 |

**解读**:

- 本实验的主机路径(Python)远低于临界值,所以近存全面占优;
- 如果换成高度优化的 C/FPGA 主机算子(例如 2 GiB/s),
  在 1 GiB/s 链路上主机就会在**大文件**上反超;
- 这正好给出论文的"适用边界":**近存计算的收益取决于"链路慢 + 设备快"**,
  而不是绝对的"存储端一定更快"。

## 5. 适用边界与威胁

| 威胁 | 影响 | 缓解 |
| --- | --- | --- |
| 只有 3 个数据点 | 截距与斜率不稳定 | 补充 8–128 MiB 多点 |
| 主机路径含 Python 计算 | 高估主机成本 | 用优化的 C/内核实现重测 |
| 共享容器环境 | 噪声大 | 真机 + 多次重复 |
| 不同算子的计算强度不同 | 模型参数不可通用 | 按算子类别分别拟合 `P_host/P_dev` |
| 缓存状态 | 冷/热差异大 | 按冷/热分别建模型 |

---

## 6. 结论

1. 本工作负载(图像检索扫描)在 4–64 MiB 区间内**明确处于近存占优区**;
2. 模型给出的判据不是"数据大就该下沉",而是
   **`1/B_link + 1/P_host` 与 `1/B_dev + 1/P_dev` 的比较**;
3. 当主机计算足够快(约 > 0.6–1.3 GiB/s,取决于链路)时,
   主机路径会在大文件上反超——这为"何时不该下沉"提供了定量边界;
4. 下一步:在 tan 集群/真机上补充规模点,按算子类别拟合参数,
   并把 break-even 相图作为论文的核心图之一。

## 7. 交叉点分析:什么时候主机更好,什么时候 CSD 更好

> 脚本:[`scripts/crossover_analysis.py`](../scripts/crossover_analysis.py)。
> 本节把端到端时延拆成"链路、主机计算、设备读取、设备算子"四个分量,
> 再比较两条路径的**边际成本**。

### 7.1 从实验数据拆出的分量

| 图库 | 块数 | B_link(MiB/s) | P_host(Python, MiB/s) | 设备读/块(MiB/s) | 设备算子/块(MiB/s) |
| --- | --- | --- | --- | --- | --- |
| 4 MiB | 1 | 248.4 | 8.2 | 571.4 | 666.7 |
| 16 MiB | 4 | 321.8 | 8.3 | 164.9 | 666.7 |
| 64 MiB | 16 | 505.1 | 8.1 | 86.5 | 666.7 |
| **中位数** | — | **321.8** | **8.2** | **164.9** | **666.7** |

说明:`B_dev/chunk` 由"设备读耗时之和 / 块数"换算,受并发与缓存影响,
数值波动较大,这里取中位数作为一阶估计。

### 7.2 边际成本与三种 CSD 形态

```text
a_host = 1/B_link + 1/P_host
a_csd  = 1/(k_read · B_dev) + 1/(k_compute · P_dev)
```

`k_read` / `k_compute` 是有效并发度,取决于设备侧 agent 的实现:

| CSD 形态 | k_read | k_compute | 边际成本(ms/MiB) |
| --- | --- | --- | --- |
| **串行**(当前 C++ agent:一次只处理一个请求) | 1 | 1 | **7.56** |
| **并发**(软件 agent/未来多线程) | 8 | 8 | **0.95** |
| **流水线**(读与算重叠,算仍串行) | 8 | 1 | **2.26** |

主机路径(取决于主机计算速率 `P_host`):

| `P_host` | 场景 | a_host(ms/MiB) |
| --- | --- | --- |
| 8.2 | 本实验的 Python 客户端 | **125.46** |
| 100 | 朴素 C/Go 实现 | 13.11 |
| 500 | 优化后的标量实现 | 5.11 |
| 1000 | SIMD/多线程 | 4.11 |
| 2000 | 高度优化 | 3.61 |

### 7.3 决策结论(固定 B_link≈322 MiB/s)

| 主机计算速率 | vs 串行 CSD | vs 并发 CSD | vs 流水线 CSD |
| --- | --- | --- | --- |
| 8.2(Python) | CSD 胜 | CSD 胜 | CSD 胜 |
| 100 | CSD 胜(13.1 > 7.56) | CSD 胜 | CSD 胜 |
| 200 | CSD 胜(8.11 > 7.56) | CSD 胜 | CSD 胜 |
| **500** | **主机胜(5.11 < 7.56)** | CSD 胜 | CSD 胜 |
| **1000** | **主机胜** | CSD 胜 | CSD 胜 |
| **2000** | **主机胜** | CSD 胜 | CSD 胜 |

### 7.4 二维判决表(B_link × P_host)

条目为"CSD 开始占优的交叉点 `S*`(MiB)";`H` 表示主机全程更优,
`C` 表示 CSD 全程更优(两种路径固定开销近似相等,故交叉点接近 0)。

| B_link \ P_host | 50 | 100 | 200 | 500 | 1000 | 2000 |
| --- | --- | --- | --- | --- | --- | --- |
| 100 MiB/s | C | C | C | C | C | C |
| 300 MiB/s | C | C | C | C | C | C |
| 1 GiB/s | C | C | C | C | C | C |
| 3 GiB/s | C | C | C | C | C | **H** |
| 10 GiB/s | C | C | C | C | C | **H** |

> 此表按**并发 CSD**(k=8)计算。若设备串行,则 P_host ≥ 500 MiB/s 时
> 主机在表中大部分格子里都会变成 H。

### 7.5 最终判据

```text
若 a_host < a_csd  → 主机计算更好
若 a_host > a_csd  → CSD 更好
若固定开销差异不可忽略:
    S* = (L_csd − L_host) / (a_host − a_csd)
    S < S* 主机更好;S > S* CSD 更好
```

本系统实测 `L_host ≈ L_csd ≈ 8.7 ms`,因此**交叉点主要由边际成本决定**,
固定开销只在极小文件(几 MiB 以下)时才有影响。

### 7.6 三条可操作的工程结论

1. **CSD 的胜负手是并发度**:并发/流水线把边际成本从 7.56 降到 0.95–2.26 ms/MiB;
   当前 C++ agent 串行处理,是最大的可优化项(P1-5)。
2. **单块文件没有扇出优势**:只有 1 个 chunk 时 k=1,CSD 退化为串行形态;
   大文件(多块)才吃得到并行收益——这与实测"4 MiB 单块延迟明显偏高"一致。
3. **主机计算足够快时,主机确实更好**:当主机计算 ≥ 500 MiB/s 且链路 ≥ 3 GiB/s 时,
   串行 CSD 会被主机反超;因此"是否下沉"必须按 `1/B_link + 1/P_host` 判断,
   不能一概而论。

### 7.7 适用边界

- 分量估计来自本地容器,链路是 loopback、设备是软件 agent;
- 真机上 `B_dev`、`P_dev` 会显著不同,必须重新拟合;
- `P_host` 强烈依赖实现语言与优化程度(本实验的 Python 仅 8.2 MiB/s);
- 并发度 k 受扇出上限(8)、设备并发和 chunk 数三者共同限制。
