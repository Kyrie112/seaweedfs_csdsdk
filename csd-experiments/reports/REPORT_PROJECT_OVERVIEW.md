# SeaweedFS + SmartSSD 可计算存储项目汇报

> 本文面向**完全没有接触过这项工作**的读者,用于向 Leader 讲解。
> 不需要任何存储或 FPGA 背景;所有术语在文末的[术语表](#9-附录术语表)里都有解释。

## 0. 一页速览(90 秒版)

**我们在做什么**:让"计算"跑到存储设备里面去执行,而不是把数据搬到服务器内存里再算。

**为什么值得做**:在数据中心里,"把数据搬来搬去"本身就是巨大的开销——
占带宽、占内存、占 CPU。数据量越大,搬数据的代价越高。

**我们做了什么**:把开源分布式存储系统 SeaweedFS 和一块带 FPGA 的智能硬盘
(SmartSSD)接起来,让 SeaweedFS 在收到"对这个文件求和"这类请求时,
把计算任务下发给硬盘内部执行,**只把结果传回来**。

**现在到什么程度**:

| 维度 | 状态 |
| --- | --- |
| 功能 | 已打通:文件/对象/块三种调用方式 → 跨多块编排 → 设备内计算 |
| 性能 | 已在本机完整部署并实测,结果正确性 100% 通过独立验证 |
| 关键修复 | 本轮修掉 5 个缺陷,其中 3 个会**静默影响结果正确性或可用性** |
| 尚未完成 | 真机(带 FPGA 的服务器)上的最终性能复测,需要重新编译一次 FPGA 固件(约 2 小时) |

**如果只记三件事**:

1. 我们把"数据搬运"从关键路径上拿掉了——原来要搬 64MB 到主机,现在只回传一个数字。
2. 我们发现并修复了一个"看起来在零拷贝、实际从未生效"的问题——这是本阶段最有价值的产出。
3. 我们建立了可复现的实验台,不需要 FPGA 也能跑完整链路,后续每个优化都能量化验证。

## 1. 背景:这件事解决什么问题

### 1.1 一个直观的例子

假设有一个 64MB 的数据文件,要算它所有数字的总和。

**传统做法**:把这 64MB 数据从硬盘读到服务器内存,再用 CPU 算。
搬了 64MB,算完就把数据扔了。

**我们的做法**:在硬盘内部算,只把"总和"这一个数字传回服务器。
搬到主机的数据量 ≈ 0。

数据量越大、计算越简单,这个差距越明显。这类"扫描型计算"(求和、过滤、
统计、特征提取)在数据分析、日志处理、AI 预处理里非常常见。

### 1.2 为什么需要"可计算存储"

现代服务器里,CPU 和内存早就比硬盘快得多,真正的瓶颈变成了**数据搬运**:

- 硬盘 → 内存:受带宽限制,是物理上限;
- 内存 → CPU:要占用内存带宽;
- 数据在缓存和缓冲区之间来回拷贝:消耗 CPU。

所以业界想了个办法:**把一小块计算能力直接放进存储设备**(通常是 FPGA),
让数据"就地算完"。这就是**可计算存储(Computational Storage)**,
也叫**近存计算 / 存内计算**。它已经是三星、Xilinx(AMD)等厂商在推的方向。

### 1.3 我们具体做了什么

两块拼图:

- **SeaweedFS**:一个开源分布式文件系统(类似"自己搭的网盘"),
  负责存文件、管理元数据。它的特点是架构简单、写入快。
- **SmartSSD**:一块内置 FPGA 的固态硬盘,可以跑我们写好的计算内核。

我们做的是**把这两者接起来**,并且解决中间所有的工程问题:
任务怎么下发、数据区间怎么描述、多块文件怎么并行、
多副本怎么选、结果怎么汇总、出错怎么兜底。

## 2. 系统是怎么工作的

一次"对文件求和"的完整流程:

```text
   用户请求                       ┌──────────────────────────┐
  (文件 / 对象 / 块)  ──────────▶ │  Filer(元数据 + 编排)    │
                                 │  ① 解析出文件由哪些块组成 │
                                 │  ② 决定每块派给哪台服务器 │
                                 └───────────┬──────────────┘
                                             │ ③ 并发下发(最多 8 路)
                                 ┌───────────▼──────────────┐
                                 │  Volume Server(数据节点) │
                                 │  ④ 只读元数据,算出这块   │
                                 │     数据在 .dat 文件里的  │
                                 │     精确位置(不读数据)   │
                                 └───────────┬──────────────┘
                                             │ ⑤ 下发"区间描述符":
                                             │    哪个文件、从哪开始、多长
                                 ┌───────────▼──────────────┐
                                 │  CSD Agent(设备侧常驻)   │
                                 │  ⑥ 从硬盘直接读进 FPGA    │
                                 │     显存(O_DIRECT + P2P)  │
                                 │  ⑦ 只回传一个小数字       │
                                 └───────────┬──────────────┘
                                             ▼
                                      SmartSSD / FPGA

   ⑧ Filer 把各块的小结果汇总成最终答案,返回给用户
```

对比一下最关键的一步:

| | 数据搬到哪里 | 主机要处理的数据量 |
| --- | --- | --- |
| 传统"读下来再算" | 硬盘 → 服务器内存 → CPU | 等于文件大小 |
| 我们的"就地算" | 硬盘 → 设备内部 | ≈ 0(只回传结果) |

## 3. 已完成的工作(逐条)

整个项目分 8 个里程碑推进,每一个都有可运行的代码和验证记录。

### V0 基线:确认"计算下沉"的起点

- **做了什么**:沿用 SeaweedFS 原有的能力——服务器收到带 `?compute=` 的请求时,
  在本地执行一个脚本。
- **解决的问题**:先有一个"能算但很笨"的版本作为对照。
  它要把整个数据读进内存、写一个临时文件、再调脚本,开销很大。
- **结果**:建立了对照基线。

### V1 多模态调用接口:让用户能用三种方式触发计算

- **做了什么**:统一了三种调用入口——按**文件路径**、按**对象**(S3 风格)、
  按**数据块**,并且支持用 S3 的请求头触发计算。
- **解决的问题**:以前只有一种偏底层的入口,不好用,也不利于对上讲"兼容性"。
- **验证**:一个由 22 个块组成的大文件,五种入口返回完全一致的结果。

### V2 区间描述符:让数据不再被"读进来"

- **做了什么**:数据节点不再把数据读进内存,而是只读一小段**元数据**,
  算出这块数据在磁盘文件里的**物理位置**,然后把
  "哪个文件、从哪个偏移、读多长"告诉设备侧。
- **解决的问题**:这是"零拷贝"的第一块基石。原来数据必须先进主机内存。
- **兜底**:如果数据是压缩存储的、或格式特殊,自动退回 CPU 计算,保证不出错。

### V3 P2P 数据通路:硬盘数据直接进 FPGA 显存

- **做了什么**:设备侧做一个常驻进程(agent),把 FPGA 的显存映射到主机地址空间,
  用 `O_DIRECT` 把磁盘数据**直接读进 FPGA 显存**,绕开主机内存和中间拷贝。
- **解决的问题**:去掉了"主机内存中转"这一步。
- **当时的状态**:人工构造的对齐请求下验证通过——**但这一条后来被我们推翻**,见下面阶段一。

### V4 CSD 感知的副本调度:优先派给"有计算能力"的节点

- **做了什么**:同一个数据可能有多个副本,调度时先探测哪个节点接了 SmartSSD,
  优先派给它能算的节点;探测结果缓存 30 秒,避免每次都问。
- **解决的问题**:以前是"随便挑一个",可能把计算任务派给了没有 FPGA 的普通节点。

### V5 负载感知调度:并发扇出时不要都挤在一个节点

- **做了什么**:调度时看每个节点的在途任务量,挑最闲的;
  并且用"原子预留"避免并发的多个任务同时选中同一个节点;
  首选节点失败时自动换下一个。
- **解决的问题**:并发时"惊群"和"失败后重试又选回同一个坏节点"。

### 跨块编排:把大文件拆开并行算,再合并结果

- **做了什么**:大文件被切成很多块分布在不同节点上。Filer 会展开块清单、
  校验它们**连续且无空洞**地覆盖整个文件,然后并发(最多 8 路)把计算派下去,
  最后把每块的小结果合并成最终答案。
- **解决的问题**:以前只支持"一个文件正好放在一块里"的情况,大文件完全用不了。
- **验证**:184.5MB / 22 块的文件,结果与 CPU 参考值一致。

### 阶段一(本轮):把核心卖点做实 + 建立实验能力

这是本次汇报的重点,详细见第 4 节。

### V7(本轮):自适应数据通路

根据实测发现的规律,让 agent **先感知数据是否已在内存缓存里,再决定走哪条路**。
详见第 4.4 节。

## 4. 本轮(阶段一)专项:做了什么、结果如何

### 4.1 最重要的发现:所谓"零拷贝"其实从未生效

**问题**:V3 里我们声称"用 O_DIRECT 把数据直接读进 FPGA 显存"。
但 `O_DIRECT` 有个硬性要求——读的起点和长度都必须是 512 字节的整数倍。

而 SeaweedFS 存储数据时,一条记录的数据区起点是
**"记录起始位置 + 20 字节"**(20 字节是文件头)。这个 `+20` 让起点几乎
永远不可能是 512 的整数倍。

**结论**:真实业务请求下,这个判断条件几乎恒为假,
所以走的还是普通的"经过内存缓存"的读法。此前的"验证通过"
是人工构造了一个对齐的请求才成立的。

**为什么不干脆在主机上把多余的头尾裁掉?**
我们的求和算法把字节按"每 8 字节打包成一个 64 位数字"再相加。
如果起点整体前移 δ 个字节,每个字节的权重都会改变——只要 δ 不是 8 的倍数,
结果就会整体变化(真实场景 δ = 20,20 不是 8 的倍数)。
**所以这件事只能交给设备端**:我们在 FPGA 内核里加了两个参数,
让它从"该算的第一个字节"开始打包。

**修复内容**:

1. 数据节点把"对齐后的读取窗口 + 该从哪里开始算"一并下发给设备;
2. FPGA 内核升级,支持从窗口内部偏移处开始计算;
3. 兼容处理:设备启动时自动识别内核版本,老固件自动退回原逻辑,
   **不会算错、也不会不可用**。

### 4.2 本轮修复的 5 个缺陷

| # | 缺陷 | 影响 | 状态 |
| --- | --- | --- | --- |
| 1 | 对齐判断恒为假 | "零拷贝"卖点从未兑现 | 已修复并实测生效 |
| 2 | 读取长度不校验 | 读到部分数据时**静默返回错误结果** | 已修复 |
| 3 | 调度器:探测时持锁 / 重试不排除失败节点 / 负载按条数而非字节 | 并发被串行化;故障重试可能选回坏节点;大块小块被同等对待 | 已修复 |
| 4 | 对齐窗口越过文件结尾 | 一个卷文件里**最后一条记录**的请求会间歇性失败 | 部署实验中暴露并修复 |
| 5 | 在 O_DIRECT 句柄上做小块补读 | 系统报 `EINVAL` 直接失败 | 部署实验中暴露并修复 |

> 注:第 4、5 条是**真正部署运行之后才暴露**的,只读代码发现不了。
> 这也是我们坚持要"跑起来验证"的原因。

### 4.3 建立可复现的实验台(本轮的工程产出)

因为我们手上没有随时可用的 FPGA 机器,我们做了一个**软件版的 CSD agent**:
它使用**完全相同的接口和计算语义**(包括上面说的偏移规则),
只是用 CPU 代替 FPGA。因此可以在一台普通机器上跑通
"Filer → 数据节点 → 设备 → 汇总"的完整链路,并量化每一处修改的效果。

实验台包括:一键部署脚本、三/四种读路径的对照实验、以及**独立的结果校验**
(用另一套实现重新算一遍做交叉验证)。

### 4.4 性能实测结果

**实验规模**:64MB 文件 → 16 个数据块;每种配置重复 9 次取中位数。

**正确性(全部通过)**:

- 54 次请求全部成功,返回**同一个数值**;
- 单块场景与 16 块聚合场景都通过了**独立实现的复算**;
- 三种读路径结果完全一致。

**性能对比**(单位:毫秒/次请求):

| 读路径 | 数据在内存缓存中(热) | 数据需要从盘上读(冷) |
| --- | --- | --- |
| 修复前语义 | 32.7 | 257.2 |
| 对齐窗口(不直读) | 32.1 | 241.6 |
| **修复后(对齐 + 直读)** | 173.8 | **188.3** |

**怎么解读**:

- 冷数据下修复后的路径最快,**端到端时延降低 26.8%**,
  设备读阶段降低 31.8%——这是实话实说的收益;
- 热数据下它反而慢 5 倍,因为直读**不走内存缓存**;
- 对齐带来的额外读取量只有 **0.0105%**(每 40MB 多读约 4KB),
  成本可以忽略。

**一个诚实的说明**:本机是共享的容器环境,页缓存能装下全部测试数据,
所以"热"场景被放大了。权威数字需要在真机上重测(见第 6 节)。

### 4.5 V7:自适应数据通路(把上面那个"反向结论"变成功能)

既然"冷数据直读快、热数据走缓存快",那就**让 agent 自己感知**:

1. 先用一个特殊系统调用(`preadv2` + `RWF_NOWAIT`)尝试读;
2. 如果**完整读成功**,说明数据已在内存里,而且这次调用本身就把数据取到了——
   零额外开销;
3. 如果失败或只读到一部分,就立刻回退到直读路径。

**结果**:

| 策略 | 热场景 | 冷场景 |
| --- | --- | --- |
| 始终直读 | 168.5 ms | 197.0 ms |
| **自适应(本次新增)** | **27.1 ms**(快 6.2 倍) | 204.5 ms(基本持平) |

也就是**拿到了两条路径各自的上界**,而代价只有噪声量级。

**同时发现一个重要边界**(已写进文档,作为下一阶段的课题):
直读**不会把数据放进内存缓存**。如果只有计算请求在访问这个文件,
缓存永远是空的,自适应就会退化成"永远直读"。
所以这个优化的收益依赖"数据也被普通读路径访问过"
(比如用户先下载过、或有副本同步)。

## 6. 尚未完成与下一步

**唯一未完成的验证**:真机(带 FPGA 的服务器)上的最终复测。
原因是它需要重新编译一次 FPGA 固件(硬件综合约 2 小时),
而这台开发机上没有 FPGA 环境。所需命令和验收标准已经写在
[阶段一报告](REPORT_PHASE1_HARDENING.md)第 9 节,拿到机器即可执行。

**下一阶段计划**(按优先级):

1. **真机复测**:重新综合固件,确认直读真正生效,补上权威性能数字;
2. **自适应缓存"自举"**:解决"只走计算路径时缓存永远为空"的问题;
3. **调度模型化**:把现在"按经验排序"的调度升级为带成本模型的全局规划,
   并给出"什么时候该下沉计算、什么时候不该"的判据;
4. **扩展算子**:从"求和"扩展到过滤、Top-K、直方图、向量距离等,
   并支持压缩数据的就地计算;
5. **完整实验矩阵**:消融实验、规模扩展、尾延迟与能耗指标。

| **Needle** | SeaweedFS 存储一条数据记录的内部格式;数据区前面有 20 字节头部 |
| **Chunk(块)** | 大文件会被切成若干块分散存放,每块通常几 MB |
| **CSD** | Computational Storage Device,可计算存储设备;本文特指带 FPGA 的 SmartSSD |
| **SmartSSD** | 内置 FPGA 的固态硬盘,可以在盘内直接跑计算 |
| **FPGA / 内核(kernel)** | 可编程硬件芯片;上面运行的硬件电路叫"内核",本项目里就是求和电路 |
| **可计算存储 / 近存计算** | 把计算放到存储设备内部执行,减少数据搬运 |
| **零拷贝** | 不做多余的数据复制,数据从磁盘直达计算单元 |
| **O_DIRECT** | 一种"绕过操作系统内存缓存直接读盘"的方式,要求地址和长度按 512 字节对齐 |
| **页缓存(page cache)** | 操作系统用内存缓存磁盘数据的机制;命中时读取很快 |
| **P2P 缓冲区** | 把 FPGA 显存映射到主机地址空间,让磁盘数据直接写进去的技术 |
| **扇出(fan-out)** | 把一个大任务拆成多个子任务并发下发给不同节点 |
| **副本(replica)** | 同一份数据的多个拷贝,用于容错和负载均衡 |
| **调度器** | 决定"这个子任务派给哪个节点"的组件 |
| **时延(latency)** | 一次请求从发出到拿到结果所花的时间 |
| **冷/热数据** | 冷 = 需要从磁盘读;热 = 已在内存缓存里 |
| **O_DIRECT 对齐窗口** | 为了让直接读盘合法,把读取范围向外扩展到 512 字节的整数倍 |

## 10. 一分钟讲稿(上台可直接用)

> 我们的项目是把分布式存储系统 SeaweedFS 和内置 FPGA 的智能硬盘结合起来,
> 让"求和、过滤、统计"这类计算**直接在硬盘里完成**,而不是把数据搬到服务器内存再算。
> 数据量越大,省下的搬运开销越可观——对 64MB 的文件求和,原来要搬 64MB,
> 现在只需要回传一个数字。
>
> 这个阶段我们做了三件事:
> 第一,**发现并修复了一个隐藏很深的问题**——之前声称的"零拷贝"因为一个 20 字节的
> 偏移,在真实场景下从未生效;我们重新设计了协议和硬件内核,让它真正生效,
> 并且兼容旧固件、保证不会算错。
> 第二,**修掉了另外 4 个缺陷**,其中两个是只有真正部署运行才暴露出来的,
> 包括一个会导致部分数据被静默算错、一个会导致特定请求间歇性失败。
> 第三,**建立了可复现的实验台**,不需要 FPGA 就能跑通全链路,
> 实测冷数据下时延降低 26.8%,并且做到了结果 100% 正确;
> 我们还顺手做了一个"自适应"版本,在数据已在缓存时快 6.2 倍。
>
> 目前唯一没做的是真机上的最终复测,因为它需要重新编译一次 FPGA 固件(约 2 小时),
> 开发机上没有硬件环境。下一步计划是完成真机复测,然后把调度从"按经验排序"
> 升级为带成本模型的全局优化。
