# 限制 Server 端 CPU 与上传带宽的影响——验证需要 CSD 近存计算

## 实验口径

- 数据文件:big_numbers.txt(176MB,3600 万个整数),位于 192.168.0.10 volume 3。
- **Server 上传带宽限制**:filer `-downloadMaxMBps`(0/6/3/1 MB/s),限制服务器→客户端的数据传输速率。
- **Server CPU 限制**:systemd `CPUQuota` 限制 .10 上 volume 进程总 CPU(100%=1 核、200%=2 核、3200%=32 核)。
- 对比对象:
  - **host**:客户端下载 176MB 后本地求和(受带宽影响,不占服务器 CPU);
  - **当前下沉**:`?compute=sum`,volume 在服务器 CPU 上执行 sum.sh 再回传结果(占服务器 CPU,结果仅 ~10B);
  - **CSD(模拟)**:无限制下的 offload 耗时 ≈17.5s,代表设备内专用引擎计算(不占服务器 CPU、只回传结果)。

---

## 影响 1:限制 Server 上传带宽

| Server 带宽 | host 总时延 | 当前下沉 | CSD(模拟) |
|---|---|---|---|
| unlim | 11.03±0.23s | 17.60±0.51s | ~17.5s |
| 6MB/s | 38.58±0.23s | 17.43±0.14s | ~17.5s |
| 3MB/s | 66.46±0.08s | 17.31±0.13s | ~17.5s |
| 1MB/s | **178.33±0.06s** | 17.61±0.13s | ~17.5s |

- 影响:带宽受限时,host 模式必须搬 176MB,时延线性恶化(11s→178s,16 倍);当前下沉与 CSD 只回传结果,几乎不受影响。
- **结论:带宽瓶颈用"结果回传"解决 → 近存计算方向正确;但仅此还不够,见影响 2。**

## 影响 2:限制 Server CPU(配额 × 并发下沉)

| CPUQuota | 并发 N=1 | N=2 | N=4 |
|---|---|---|---|
| 100% (1核) | 17.9s ✓ | **失败 0/2**(36s/7s) | **失败 0/4**(42s/14s) |
| 200% (2核) | 17.5s ✓ | 17.6s ✓ | **失败 0/4**(37s/7s) |
| 3200% (32核) | 17.6s ✓ | 17.7s ✓ | 18.0s ✓(4/4) |

- 影响:单请求时 CPU 配额几乎无影响(awk 单线程);一旦并发,配额紧(1~2 核)时当前下沉
  **全面失败**(`context canceled`/连接错误),只有配额充足才稳定。
- 原因:当前下沉把计算放在**服务器 CPU**上,CPU 是共享有限资源,并发请求争抢导致 Go 服务
  无法维持多个计算管道。
- **结论:带宽问题解决了,CPU 问题还在 → 必须把计算移出服务器 CPU。**

## 汇总:为什么需要 CSD

| 资源受限场景 | host(先搬数据再算) | 当前下沉(服务器 CPU 上算) | CSD(设备内引擎) |
|---|---|---|---|
| Server 带宽受限(1MB/s) | 178.3s(差 16x) | 17.6s(好) | ~17.5s(好) |
| Server CPU 受限 + 并发(1~2 核,4 并发) | 不占服务器 CPU | **失败(0/4,不可用)** | **正常(每设备独立引擎)** |
| 回传数据量 | 176MB | ~10B | ~10B |

**验证结论**:

1. 限制 Server 上传带宽 → host 模式不可行(时延 178s),必须把计算放到数据所在处(近存计算);
2. 限制 Server CPU → 当前"下沉到服务器 CPU"的方式在并发下失败,说明它只是把 CPU 压力从
   客户端搬到了服务器,没有真正解决资源瓶颈;
3. 只有 CSD(FPGA 引擎)既不走服务器带宽(只回结果)、又不占服务器 CPU(设备内计算),
   才能同时通过这两类限制场景的考验 → **需要 CSD 支持来解决**。
