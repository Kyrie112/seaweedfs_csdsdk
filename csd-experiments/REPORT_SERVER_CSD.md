# 当前"计算只下沉到 Server 端"的不足——为 CSD 近存计算做铺垫

## 1. 论点

当前架构的"计算下沉"实现是:**volume 服务器读到数据后,在服务器 CPU 上执行脚本(sum.sh)
再回传结果**。它仍然依赖服务器 CPU 和服务器网络栈。本报告用两组实验验证该方式的不足:

1. **带宽不足**:Server 上传带宽受限时,把数据搬到主机计算(host 模式)代价巨大;
2. **CPU 不足**:Server CPU 配额受限时,并发下沉请求变慢甚至失败(服务不可用)。

因此,只有当计算真正下沉到**存储设备内部(CSD/FPGA,专用引擎、不占服务器 CPU、只回传结果)**
时,才能同时摆脱服务器带宽和 CPU 的约束。本报告为后续 CSD 部署提供量化依据。
(真实 FPGA 计算任务不在此次范围内;`?compute=sum` 用于模拟近存计算,无限制时的
offload 耗时作为设备侧计算基线。)

## 2. 实验 A:Server 上传带宽受限 → 主机端计算不足

方法与数据见 `REPORT_SERVER.md`(filer `-downloadMaxMBps` 限速,176MB 文件):

| Server 带宽 | host 总耗时 | offload 耗时 | 加速比 |
|---|---|---|---|
| unlim | 11.0–11.2s | 17.4–17.9s | 0.61–0.64x |
| 6MB/s | 38.5–38.8s | 17.3–17.5s | 2.20–2.22x |
| 3MB/s | 66.4–66.5s | 17.3–17.5s | 3.82–3.85x |
| 1MB/s | 178.3–178.4s | 17.5–17.7s | 10.10–10.18x |

最优配置确认(8 次重复):Server 2c + 1MB/s → **host 178.333±0.063s vs offload 17.525±0.106s,
加速比 10.176x(CV 0.04%/0.61%)**。

结论:**带宽是 Server 侧最敏感的资源**;带宽受限时"先搬数据再算"线性恶化,近存计算只回传
结果几乎不受影响。这是"必须近存计算"的第一层证据。

## 3. 实验 B:Server CPU 配额受限 → 当前下沉(服务器 CPU 上计算)不足

用 systemd `CPUQuota` 限制 .10 上 volume 进程可用的总 CPU(100%=1 核、200%=2 核、
3200%=32 核),然后并发发起 1/2/4 个 `?compute=sum` 请求(每个 3 次重复),
记录整体墙钟时间与成功数(ok_count/N):

| CPUQuota | 并发 N | wall(3 次重复) | 成功率 | 结果 |
|---|---|---|---|---|
| 100% (1核) | 1 | 17.9 / 17.9 / 18.1s | 1/1 | 正常 |
| 100% | 2 | 36.2 / 7.1 / 7.2s | 0/2 | 失败(context canceled/连接错误) |
| 100% | 4 | 42.2 / 14.4 / 13.7s | 0/4 | 失败 |
| 200% (2核) | 1 | 17.3–17.6s | 1/1 | 正常 |
| 200% | 2 | 17.6–17.6s | 2/2 | 正常 |
| 200% | 4 | 36.8 / 7.1 / 7.4s | 0/4 | 失败 |
| 3200% (32核) | 1 | 17.6–17.9s | 1/1 | 正常 |
| 3200% | 2 | 17.6–17.7s | 2/2 | 正常 |
| 3200% | 4 | 17.9–18.9s | 4/4 | 正常 |

要点:

- **单请求**:CPU 配额大小几乎无影响(~17.5s,awk 单线程),说明"下沉到服务器 CPU"在小负载下
  看似高效;
- **并发即暴露**:CPU 配额只有 1 核时,2 个并发请求就全部失败;2 核时 4 个并发请求全部失败;
  只有配额充足(32 核)时 4 并发才稳定(~18s,4/4 成功)。
- 失败模式:volume 的 Go HTTP 服务在 CPU 紧张时无法维持多个计算管道,请求以
  `compute operation "sum" failed: context canceled` 或连接错误快速失败。
- 补充观察:把 volume 钉到单核再叠加 busy-loop(争抢)会导致单请求从 ~17s 恶化到数分钟且
  sshd 失联(见 `REPORT_SERVER.md` 2.2),进一步说明服务器 CPU 争抢的脆弱性。

结论:**当前下沉把计算放在服务器 CPU 上,CPU 是共享、有限资源**;服务器 CPU 配额紧时,
并发近存计算变慢甚至不可用。这是"必须把计算移出服务器 CPU(CSD)"的第二层证据。

## 4. 综合结论:为什么需要 CSD

| 场景 | 主机端计算 | 当前下沉(服务器 CPU) | CSD(设备内引擎) |
|---|---|---|---|
| Server 带宽受限 | 差(10x 恶化) | 好(只传结果) | 好(只传结果) |
| Server CPU 受限 | 不涉及服务器 CPU | **差(并发失败/串行)** | **好(专用引擎,不占服务器 CPU)** |
| 结果回传 | 176MB | 10B | 10B |

当前"只下沉到 Server 端"解决了带宽问题,但没有解决 CPU 问题——它把计算从客户端 CPU
搬到了服务器 CPU,服务器 CPU 一紧张,计算照样退化或不可用。只有 CSD 把计算放进存储设备
(FPGA 引擎),才能同时规避服务器带宽与 CPU 两个瓶颈。本实验数据(带宽下 10.18x、
CPU 配额下并发不可用)即为后续 CSD 部署的基线证据。
